🔷 Интерфейсы vs Абстрактные классы

Один из самых частых вопросов: "Чем отличается интерфейс от абстрактного класса?" — отвечаем чётко.

Главные различия

ХарактеристикаАбстрактный классИнтерфейс
Ключевое словоabstract classinterface
Наследованиеextends (только 1)implements (много)
ПоляЛюбые (могут быть не static/final)Только public static final
Методы с телом✅ Обычные методы✅ default и static (Java 8+)
Конструктор✅ Есть❌ Нет
МодификаторыЛюбыеНеявно public
Множественное❌ Нет (ромбовидная проблема)✅ Да (default-методы разрешают конфликт)
Абстрактный класс может содержать состояние (поля) и частичную реализацию, наследуется через extends (только один). Интерфейс описывает контракт, не хранит состояние, реализуется через implements (можно много). Абстрактный класс — когда есть общее состояние; интерфейс — когда нужен только контракт.

Абстрактный класс — подробно

Это "полуфабрикат": общая часть у всех наследников, но сам по себе — неполный.

public abstract class Animal {
    protected String name;  // состояние — общее для всех

    public Animal(String name) {
        this.name = name;
    }

    public void sleep() {   // общая реализация
        System.out.println(name + " спит");
    }

    public abstract void makeSound(); // каждый по-своему
}

public class Dog extends Animal {
    public Dog(String name) { super(name); }

    @Override
    public void makeSound() {
        System.out.println(name + ": Гав!");
    }
}

// Animal a = new Animal("Кто-то"); // ❌ Нельзя! Абстрактный
Dog dog = new Dog("Шарик");        // ✅ Можно
dog.sleep();     // Шарик спит
dog.makeSound(); // Шарик: Гав!

Когда применять абстрактный класс:

  • ✅ Есть общее состояние (поля)
  • ✅ Есть общая реализация методов
  • ✅ Нужно запретить создание родителя
  • ❌ Не подходит, если нужно наследовать несколько

Интерфейс — подробно

Только контракт: ЧТО делать, но не КАК.

public interface Flyable {
    void fly(); // неявно public abstract
}

public interface Swimable {
    void swim();
}

// Множественная реализация
public class Duck implements Flyable, Swimable {
    @Override
    public void fly() { System.out.println("Утка летит"); }

    @Override
    public void swim() { System.out.println("Утка плывёт"); }
}

default-методы (Java 8+)

Позволяют добавить реализацию в интерфейс, не ломая существующий код.

public interface Loggable {
    default void log(String msg) {
        System.out.println("[LOG] " + msg);
    }
}

public class MyService implements Loggable {
    // log() уже есть, можно не переопределять
    public void doSomething() {
        log("Что-то делаем"); // [LOG] Что-то делаем
    }
}

Проблема ромба (diamond problem)

Когда два интерфейса дают default-метод с одинаковой сигнатурой — класс обязан разрешить конфликт.

public interface A {
    default void greet() { System.out.println("A"); }
}

public interface B {
    default void greet() { System.out.println("B"); }
}

// ❌ Так нельзя — конфликт!
// public class MyClass implements A, B { }

// ✅ Так можно — явно указываем
public class MyClass implements A, B {
    @Override
    public void greet() {
        A.super.greet(); // или B.super.greet(), или своя логика
    }
}

Почему в Java нет множественного наследования классов: чтобы избежать проблемы ромба на уровне состояния (какое поле использовать?). С интерфейсами проще — там нет состояния, только поведение.

Когда что выбирать

СитуацияВыбор
Нужно общее состояние (поля)Абстрактный класс
Нужно только поведение (контракт)Интерфейс
Нужна множественная "наследственность"Интерфейс (их можно много)
Хочу дать реализацию "по умолчанию"default-метод в интерфейсе или метод в абстрактном классе
Сторонний класс должен встроиться в мою системуИнтерфейс (нельзя унаследовать чужой класс)
Выбираем абстрактный класс, когда есть общее состояние и реализация. Выбираем интерфейс, когда нужен только контракт, или когда классу нужно реализовать несколько разных поведений.
