📦 Redis

Redis — in-memory хранилище данных. Используется как кеш, брокер сообщений, хранилище сессий. Скорость — микросекунды.

Что такое Redis и зачем он нужен

ПроблемаБез RedisС Redis
Частые запросы к БДКаждый раз SQL-запрос (10-50ms)Данные в Redis (< 1ms)
Сессии пользователейХранятся в памяти сервера (пропадают при рестарте)Хранятся в Redis (живут независимо)
Очереди задачНужен отдельный брокерRedis Pub/Sub или List как очередь
Счётчики (лайки, просмотры)UPDATE в БД — медленноINCR в Redis — атомарно и быстро
Redis — это in-memory key-value хранилище. Все данные в оперативной памяти, поэтому операции выполняются за микросекунды. Используется как кеш (чтобы не ходить в БД), хранилище сессий, счётчики, Pub/Sub, очереди. Данные можно сохранять на диск (RDB/AOF).

Типы данных в Redis

ТипПримерИспользование
StringSET key "value"Кеш JSON, счётчики (INCR)
ListLPUSH queue "task1"Очереди задач (LPUSH + RPOP)
SetSADD tags "java" "spring"Уникальные теги, общие друзья
HashHSET user:1 name "Ivan" age 25Объекты (пользователь, товар)
Sorted SetZADD leaderboard 100 "player1"Рейтинги, таблицы лидеров

Примеры команд:

# String
SET user:1 '{"name":"Иван","age":25}'
GET user:1
INCR page:views       # увеличить счётчик на 1

# List (очередь)
LPUSH tasks "email:1"  # добавить в начало
RPOP tasks             # взять с конца (FIFO)

# Set
SADD friends:1 "user:2" "user:3"
SINTER friends:1 friends:2  # общие друзья

# Hash
HSET user:1 name "Иван" age 25 email "ivan@mail.ru"
HGET user:1 name      # "Иван"
HGETALL user:1        # все поля

# Sorted Set (рейтинг)
ZADD leaderboard 1000 "player1" 500 "player2"
ZREVRANGE leaderboard 0 9  # топ-10

Spring Boot + Redis

Зависимость:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>

Настройка (application.properties):

spring.data.redis.host=localhost
spring.data.redis.port=6379
spring.cache.type=redis

Кеширование через @Cacheable:

@Service
public class UserService {

    @Autowired
    private UserRepository repo;

    @Cacheable(value = "users", key = "#id")
    public User findById(Long id) {
        // Первый вызов — идёт в БД и сохраняет в Redis
        // Второй вызов — берёт из Redis (без запроса в БД!)
        return repo.findById(id).orElseThrow();
    }

    @CacheEvict(value = "users", key = "#id")
    public void updateUser(Long id, UserDTO dto) {
        // Обновляем БД и сбрасываем кеш
    }

    @CachePut(value = "users", key = "#result.id")
    public User create(UserDTO dto) {
        return repo.save(new User(dto));
    }
}

Cache Aside (ручное управление):

@Service
public class UserService {

    @Autowired
    private RedisTemplate<String, User> redis;

    public User findById(Long id) {
        String key = "user:" + id;

        // 1. Проверяем кеш
        User cached = redis.opsForValue().get(key);
        if (cached != null) return cached;

        // 2. Кеша нет — идём в БД
        User user = repo.findById(id).orElseThrow();

        // 3. Кладём в кеш на 10 минут
        redis.opsForValue().set(key, user, Duration.ofMinutes(10));

        return user;
    }
}

TTL — время жизни ключа

# Redis CLI
SET temp:data "value"
EXPIRE temp:data 60    # удалится через 60 секунд
TTL temp:data          # посмотреть оставшееся время

# Spring
redis.opsForValue().set(key, value, Duration.ofMinutes(10));

Стратегии инвалидации кеша

СтратегияОписаниеКогда
TTL (Time To Live)Ключ живёт N секунд, потом удаляетсяДанные, которые устаревают предсказуемо
Cache-AsideПриложение само управляет: прочитал → положил, обновил → удалилСамый частый паттерн
Write-ThroughПишем и в БД, и в кеш одновременноДанные должны быть всегда актуальны
Write-BehindПишем в кеш, в БД — асинхронно потомВысокая скорость записи

Три проблемы кеширования

ПроблемаОписаниеРешение
Cache PenetrationЗапрашивают ключ, которого нет ни в кеше, ни в БД (DDoS)Кешировать "пустые" значения с коротким TTL
Cache BreakdownГорячий ключ истекает, и тысячи запросов летят в БД одновременноБлокировка: только один поток идёт в БД, остальные ждут
Cache AvalancheМного ключей истекают одновременноСлучайный разброс TTL (±10%)
