🧩 Микросервисная архитектура

Микросервисы — архитектурный стиль, где приложение разбито на независимые сервисы. На собесе на джуна спросят отличия от монолита и основные паттерны.

Монолит vs Микросервисы

МонолитМикросервисы
СтруктураОдно приложение, один кодМного независимых сервисов
ДеплойВесь сразуКаждый сервис отдельно
МасштабированиеВсё приложение целикомТолько нагруженные сервисы
ТехнологииОдин стекРазные стеки для разных сервисов
База данныхОдна общая БДУ каждого сервиса своя БД
КомандыОдна командаНезависимые команды
ОтказоустойчивостьУпало всё → не работает ничегоУпал один сервис → остальные работают
В монолите всё приложение — единое целое. Проще разрабатывать и тестировать, но сложнее масштабировать. В микросервисах каждый сервис независим: свой код, своя БД, свой деплой. Можно масштабировать только нагруженные сервисы, но сложнее управлять (нужен Service Discovery, мониторинг, распределённые транзакции).

Когда что выбирать

МонолитМикросервисы
✅ Стартап, MVP✅ Большая система с множеством модулей
✅ Небольшая команда (до 10 чел)✅ Много независимых команд
✅ Простая бизнес-логика✅ Нужно масштабировать части независимо
✅ Нет требований к отказоустойчивости✅ Высокие требования к доступности

Золотое правило: начинай с монолита. Разбивай на микросервисы только когда есть реальная потребность.

Как микросервисы общаются между собой

Синхронно (HTTP/REST)

// Сервис Заказов вызывает Сервис Пользователей по HTTP
@Service
public class OrderService {
    @Autowired
    private RestTemplate restTemplate;

    public Order createOrder(OrderRequest request) {
        // Вызов другого сервиса
        User user = restTemplate.getForObject(
            "http://user-service/api/users/" + request.getUserId(),
            User.class
        );
        // создаём заказ...
    }
}

Асинхронно (очереди сообщений)

// Сервис Заказов кидает сообщение в Kafka
@Service
public class OrderService {
    @Autowired
    private KafkaTemplate<String, OrderEvent> kafka;

    public Order createOrder(OrderRequest request) {
        Order order = orderRepo.save(new Order(request));
        kafka.send("order-created", new OrderEvent(order.getId()));
        // Сервис Уведомлений сам прочитает и отправит email
        return order;
    }
}

Синхронно vs Асинхронно:

Синхронно (HTTP/gRPC)Асинхронно (Kafka/RabbitMQ)
ОтветСразуКогда-нибудь
СвязанностьСильная (ждём ответ)Слабая (отправили и забыли)
ОтказоустойчивостьУпал сервис-получатель → ошибкаСообщение сохранится и обработается позже
КогдаНужен ответ прямо сейчасФоновые задачи (email, отчёты)

Service Discovery — как сервисы находят друг друга

Проблема: сервисов много, они запускаются на разных портах, могут перемещаться. Как сервису А узнать адрес сервиса Б?

Без Service Discovery:
order-service → http://user-service:8081  // жёстко зашит URL

С Service Discovery (Eureka/Consul):
order-service → спрашивает Eureka: "где user-service?"
Eureka → отвечает: "вот 3 экземпляра: 192.168.1.10:8081, 192.168.1.11:8081, ..."
order-service → выбирает один (балансировка) и вызывает
// Spring Cloud + Eureka
@FeignClient(name = "user-service") // имя сервиса, не URL!
public interface UserClient {
    @GetMapping("/api/users/{id}")
    User getUser(@PathVariable Long id);
}

// Feign сам спросит Eureka и сделает HTTP-запрос

API Gateway — единая точка входа

Проблема: фронтенду нужно стучаться в 10 разных сервисов. У каждого свой URL, свой порт.

Решение: API Gateway (Spring Cloud Gateway) — единая точка входа, которая маршрутизирует запросы.

Клиент → http://api.example.com
              ↓
        API Gateway
         /    |    \
        /     |     \
   user-svc  order-svc  payment-svc

GET /api/users/123    → маршрутизируется в user-service
POST /api/orders      → маршрутизируется в order-service

Основные паттерны микросервисов

ПаттернПроблемаРешение
Service Discovery Как сервисам найти друг друга? Eureka, Consul, Kubernetes Service
API Gateway Куда стучаться фронтенду? Spring Cloud Gateway, Kong, Nginx
Circuit Breaker Что делать, если сервис упал? Resilience4j, Hystrix
Config Server Где хранить настройки всех сервисов? Spring Cloud Config
Saga Как делать транзакции между сервисами? Оркестрация (Kafka) или хореография
CQRS Как разделить чтение и запись? Отдельные БД для чтения и записи

Circuit Breaker (предохранитель)

Проблема: если user-service упал, а order-service продолжает слать запросы — запросы копятся, потоки зависают, order-service тоже падает (каскадный отказ).

// Circuit Breaker: если user-service не отвечает 5 раз подряд —
// перестаём вызывать его на 30 секунд, сразу возвращаем fallback

@CircuitBreaker(name = "userService", fallbackMethod = "getUserFallback")
public User getUser(Long id) {
    return userClient.getUser(id);
}

public User getUserFallback(Long id, Throwable t) {
    return new User(id, "Неизвестно", "unknown@email"); // заглушка
}

Состояния Circuit Breaker:

  1. CLOSED — всё работает, запросы проходят
  2. OPEN — сервис упал, запросы не шлём, сразу fallback
  3. HALF-OPEN — пробуем один запрос: если ок → CLOSED, если ошибка → OPEN

Saga — распределённые транзакции

Проблема: в монолите — одна БД, один commit/rollback. В микросервисах — у каждого своя БД. Как откатить изменения в нескольких сервисах?

Пример: создание заказа
1. OrderService: создать заказ (своя БД)
2. PaymentService: списать деньги (своя БД)
3. InventoryService: зарезервировать товар (своя БД)

Если на шаге 3 ошибка — нужно откатить шаги 1 и 2!

Решение — Saga (цепочка компенсирующих транзакций):
- OrderService создал заказ → отправил событие
- PaymentService списал деньги → отправил событие
- InventoryService: ОШИБКА! → отправил событие "отмена"
- PaymentService: вернул деньги (компенсация)
- OrderService: отменил заказ (компенсация)
