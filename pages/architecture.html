🏗 Архитектура высоконагруженных систем

На джуна не спросят строить high-load, но могут спросить общие принципы: кеширование, репликация, очереди, CQRS.

Три уровня оптимизации

УровеньЧто делаемИнструменты
Разные инструменты JPA для простого, JDBC для сложного Hibernate + JdbcTemplate
Разделение чтения/записи Читаем с реплик, пишем в мастер CQRS, репликация БД
Асинхронность Не ждём результат, обрабатываем в фоне @Async, Kafka, RabbitMQ
В высоконагруженных системах нагрузку распределяют на нескольких уровнях: горизонтальное масштабирование (балансировщик + несколько экземпляров), разделение чтения/записи (CQRS + реплики), кеширование (Redis), асинхронная обработка (Kafka). Каждый инструмент — для своей задачи.

Горизонтальное масштабирование

Запускаем не один сервер, а несколько копий приложения за балансировщиком (Nginx).

               Балансировщик (Nginx)
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
    Сервер 1      Сервер 2      Сервер 3
  (Spring App)  (Spring App)  (Spring App)
        ↓             ↓             ↓
        └─────────────┼─────────────┘
                      ↓
               База данных

Правила:

  • Приложение должно быть stateless — не хранить состояние (сессии, кеш) в памяти сервера
  • Сессии и кеш — в Redis, файлы — в S3/MinIO
  • Балансировщик распределяет запросы (round-robin, least-connections)

CQRS — разделение чтения и записи

Command Query Responsibility Segregation — команды (изменение) и запросы (чтение) обрабатываются отдельно.

Пользователь → REST API
                ↓
        ┌──────┴──────┐
        ↓              ↓
    Команды          Запросы
  (INSERT/UPDATE)   (SELECT)
        ↓              ↓
    Мастер БД       Реплика БД (read-only, может быть несколько)
        ↓              
   Репликация (автоматически, master → replica)

Пример в Spring:

@Service
public class OrderService {

    @Transactional // → в мастер (запись)
    public void createOrder(Order order) {
        orderRepo.save(order);
    }

    @Transactional(readOnly = true) // → в реплику (чтение)
    public List<Order> getOrders() {
        return orderRepo.findAll();
    }
}

Кеширование

Правило: чем ближе кеш к пользователю — тем быстрее, но тем меньше данных.

Уровень кешаТехнологияСкоростьОбъём
Кеш браузера / CDNHTTP-заголовки, Cloudflare⚡⚡⚡ МгновенноМаленький
Кеш приложения (L2)Hibernate L2, Caffeine⚡⚡ В памяти JVMСредний
Распределённый кешRedis, Hazelcast⚡ По сетиБольшой
База данныхPostgreSQL, MySQL🐢 ДискОгромный

Паттерны кеширования:

// Cache-Aside (самый частый)
public Order getOrder(Long id) {
    // 1. Проверяем кеш
    Order cached = redis.get("order:" + id);
    if (cached != null) return cached;

    // 2. Кеша нет — идём в БД
    Order order = orderRepo.findById(id).orElseThrow();

    // 3. Кладём в кеш
    redis.set("order:" + id, order, Duration.ofMinutes(10));

    return order;
}

// В Spring — ещё проще:
@Cacheable(value = "orders", key = "#id")
public Order getOrder(Long id) { ... }

@CacheEvict(value = "orders", key = "#id") // сбросить кеш
public void updateOrder(Long id, OrderDTO dto) { ... }

Асинхронная обработка

Долгие операции (email, генерация отчётов) не должны блокировать пользователя.

Простой способ — @Async:

@Service
public class EmailService {

    @Async  // выполнится в отдельном потоке
    public void sendWelcomeEmail(User user) {
        // отправка email (3 секунды)
    }
}

// Вызов:
@Transactional
public void register(User user) {
    userRepo.save(user);           // 50ms
    emailService.sendWelcomeEmail(user); // поставили в очередь, сразу вернулись
    // Пользователь получил ответ через 50ms, а не через 3 секунды!
}

⚠ Минус: если сервер упадёт — задача потеряется.

Надёжный способ — очередь сообщений:

Пользователь → Сервис A (регистрация)
                   ↓
              Kafka (сообщение: "новый юзер 123")
                   ↓
              Сервис B (email-рассылка) — читает и отправляет
// Сервис A — кидаем сообщение
@Service
public class RegistrationService {
    @Autowired
    private KafkaTemplate<String, UserEvent> kafka;

    @Transactional
    public void register(User user) {
        userRepo.save(user);
        kafka.send("user-registered", new UserEvent(user.getId(), user.getEmail()));
        // Всё! Дальше — забота других сервисов
    }
}

// Сервис B — слушаем и отправляем email
@Service
public class EmailListener {
    @KafkaListener(topics = "user-registered")
    public void onUserRegistered(UserEvent event) {
        emailService.sendWelcome(event.getEmail());
        // Если упало — Kafka сохранит offset и повторит
    }
}

                    ↓
              S3 / MinIO (файлы, изображения)
