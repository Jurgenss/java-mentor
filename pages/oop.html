🏛 ООП — 4 принципа

Объектно-Ориентированное Программирование — основа Java. На собеседовании спросят 100%.

Четыре принципа ООП

ПринципСутьРеализация в Java
Инкапсуляция Скрытие внутреннего состояния, защита от некорректного использования private поля + публичные геттеры/сеттеры с проверками
Наследование Создание нового класса на основе существующего, отношение "is-a" extends (только 1 класс). Все классы неявно от Object
Полиморфизм Способность объекта вести себя по-разному в зависимости от реального типа Статический (overloading) + динамический (overriding) + ссылки родительского типа
Абстракция Выделение общего поведения, сокрытие деталей реализации abstract class, interface

1. Инкапсуляция

Скрываем поля от прямого доступа извне. Доступ только через методы с проверками.

public class Account {
    private double balance; // скрыто!

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма должна быть положительной!");
        }
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount > balance) {
            throw new IllegalArgumentException("Недостаточно средств!");
        }
        balance -= amount;
    }
}

Что даёт: нельзя напрямую сделать account.balance = -100000. Только через методы, которые проверяют корректность.

Инкапсуляция — это сокрытие внутреннего состояния объекта и предоставление доступа только через публичные методы. Реализуется через private поля + геттеры/сеттеры с проверками. Позволяет контролировать корректность данных.

2. Наследование

Класс-потомок получает поля и методы класса-родителя. В Java — только один родитель через extends.

// Родитель
public class Animal {
    protected String name;

    public Animal(String name) {
        this.name = name;
    }

    public void eat() {
        System.out.println(name + " ест");
    }
}

// Потомок
public class Dog extends Animal {
    public Dog(String name) {
        super(name); // вызов конструктора родителя — обязательно!
    }

    public void bark() {
        System.out.println(name + " гавкает");
    }
}

// Использование
Dog dog = new Dog("Шарик");
dog.eat();  // метод родителя
dog.bark(); // свой метод

Ограничения:

  • Множественное наследование классов запрещено (только 1 extends)
  • Конструкторы не наследуются, но вызываются через super()
  • final класс нельзя наследовать (например, String)
  • Все классы неявно наследуются от Object
Наследование — механизм, при котором класс-потомок получает поля и методы класса-родителя. В Java запрещено множественное наследование классов, но можно реализовать много интерфейсов через implements. Конструкторы не наследуются, но вызываются через super().

3. Полиморфизм

Два вида: перегрузка (overloading) и переопределение (overriding).

Overloading (перегрузка) — статический полиморфизм

Один метод с разными параметрами в одном классе. Решается на этапе компиляции.

public class Calculator {
    public int sum(int a, int b) {
        return a + b;
    }

    public double sum(double a, double b) {
        return a + b;
    }

    public int sum(int a, int b, int c) {
        return a + b + c;
    }
}

Компилятор сам выбирает нужный метод по параметрам вызова.

Overriding (переопределение) — динамический полиморфизм

Дочерний класс меняет поведение метода родителя. Решается во время выполнения.

public class Animal {
    public void speak() {
        System.out.println("Животное говорит");
    }
}

public class Cat extends Animal {
    @Override
    public void speak() {
        System.out.println("Мяу!");
    }
}

public class Dog extends Animal {
    @Override
    public void speak() {
        System.out.println("Гав!");
    }
}

// Полиморфизм в действии:
Animal[] animals = {new Cat(), new Dog(), new Animal()};
for (Animal a : animals) {
    a.speak(); // Мяу! Гав! Животное говорит
}
// Вызывается метод реального типа объекта, а не тип ссылки!
OverloadingOverriding
Когда решаетсяКомпиляцияВыполнение (JVM)
ГдеВ одном классеРодитель-наследник
СигнатураРазные параметрыОдинаковая
АннотацияНе нужна@Override
Модификатор доступаЛюбойНельзя сужать
Полиморфизм бывает двух видов: статический (overloading — перегрузка методов, решается при компиляции) и динамический (overriding — переопределение методов, решается во время выполнения по реальному типу объекта). Пример: ссылка Animal a = new Dog(); a.speak(); вызовет метод Dog.

4. Абстракция

Выделяем общее поведение, скрываем детали. Реализуется через abstract class и interface.

// Интерфейс — контракт (ЧТО делать)
public interface Drawable {
    void draw(); // абстрактный метод — нет тела
}

// Абстрактный класс — общая реализация
public abstract class Shape {
    protected String color;

    public Shape(String color) {
        this.color = color;
    }

    public abstract double getArea(); // абстрактный — без тела

    public void printColor() {       // обычный — с телом
        System.out.println("Цвет: " + color);
    }
}

// Конкретный класс
public class Circle extends Shape implements Drawable {
    private double radius;

    public Circle(String color, double radius) {
        super(color);
        this.radius = radius;
    }

    @Override
    public double getArea() {
        return Math.PI * radius * radius;
    }

    @Override
    public void draw() {
        System.out.println("Рисуем круг цвета " + color);
    }
}
Абстракция — выделение общего поведения и сокрытие деталей. Реализуется через abstract class (может содержать состояние и частичную реализацию) и interface (только контракт, что делать).

🔍 Абстрактный класс — когда и зачем

Абстрактный класс — это "полуфабрикат": часть логики общая для всех наследников, часть — уникальная.

Когда применять:

  • ✅ Есть общее состояние (поля) для всех наследников
  • ✅ Есть общая реализация методов
  • ✅ Хотим запретить создавать экземпляр родителя (нет смысла создавать "просто животное")
  • ❌ Не подходит, если нужно только поведение без состояния — тогда интерфейс

Наглядный пример: платёжная система

// Абстрактный класс — общая логика для всех платежей
public abstract class Payment {
    protected String orderId;
    protected BigDecimal amount;
    protected String status;

    public Payment(String orderId, BigDecimal amount) {
        this.orderId = orderId;
        this.amount = amount;
        this.status = "NEW";
    }

    // Общий метод с логикой — одинаков для всех
    public void validate() {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Сумма должна быть > 0");
        }
        System.out.println("Платёж " + orderId + " проверен");
    }

    // Абстрактный метод — каждый платёж выполняет по-своему
    public abstract void process();

    // Общий метод — логика едина
    public void setStatus(String status) {
        this.status = status;
        System.out.println("Статус платежа " + orderId + ": " + status);
    }
}

// Конкретная реализация — карта
public class CardPayment extends Payment {
    private String cardNumber;

    public CardPayment(String orderId, BigDecimal amount, String cardNumber) {
        super(orderId, amount); // обязательно вызываем конструктор родителя!
        this.cardNumber = cardNumber;
    }

    @Override
    public void process() {
        validate();                              // общий метод
        // Специфичная логика для карты
        System.out.println("Списываем с карты " + maskCard(cardNumber));
        setStatus("PAID");                       // общий метод
    }

    private String maskCard(String card) {
        return "****" + card.substring(card.length() - 4);
    }
}

// Конкретная реализация — QR-код
public class QrPayment extends Payment {
    private String qrCode;

    public QrPayment(String orderId, BigDecimal amount, String qrCode) {
        super(orderId, amount);
        this.qrCode = qrCode;
    }

    @Override
    public void process() {
        validate();                              // та же проверка
        System.out.println("Сканируем QR: " + qrCode);
        setStatus("PAID");
    }
}

// Использование
Payment cardPay = new CardPayment("ORD-001", new BigDecimal("1500"), "4111222233334444");
cardPay.process();
// Вывод:
// Платёж ORD-001 проверен
// Списываем с карты ****4444
// Статус платежа ORD-001: PAID

Payment qrPay = new QrPayment("ORD-002", new BigDecimal("500"), "QR-ABC123");
qrPay.process();
// Вывод:
// Платёж ORD-002 проверен
// Сканируем QR: QR-ABC123
// Статус платежа ORD-002: PAID

Что даёт абстрактный класс:

ПроблемаБез абстрактного классаС абстрактным классом
Дублирование кода validate() и setStatus() копируем в каждый класс Пишем один раз в родителе
Забытая проверка Можно забыть вызвать validate() в новом типе платежа process() обязан быть реализован, а в нём уже вызываем validate()
Создание "неправильного" объекта new Payment() — бессмысленно Payment абстрактный — создать нельзя, только конкретные

Когда использовать абстрактный класс? Когда есть общее состояние (поля, которые нужны всем наследникам) и общая реализация методов. Например, в платёжной системе: у всех платежей есть orderId, amount, status и метод validate(). Выносим их в абстрактный Payment, а каждый конкретный платёж реализует только process() по-своему. Если нужно только поведение без состояния — берём интерфейс.
